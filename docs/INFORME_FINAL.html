Resumen ejecutivo. Se implementó un servidor de chat federado en FastAPI con SQLite, reloj de Lamport, cola de salida persistente, deduplicación por UUID y recuperación por historial. La suite tiene 53 pruebas aprobadas. En el experimento real de tres repeticiones se enviaron 120 mensajes, se perdieron 7, hubo 0 duplicados y la recuperación media fue de 1.808 s. La hipótesis se cumple parcialmente: no hubo duplicados, pero la primera repetición perdió 7 mensajes. El ensayo local de interoperabilidad envió 40 mensajes con 0 faltantes, 0 duplicados y recuperación completa tras una caída de 5.664 s.

1. Introducción y objetivos

1.1 Contexto y problema

El proyecto implementa el mínimo común de un chat distribuido entre grupos de la asignatura. La arquitectura es en estrella: cada grupo corre un servidor propio y un servidor central conoce a todos. Los grupos no se hablan directamente; todo mensaje pasa por el central, que registra, guarda y reenvía.

El problema central es la tolerancia a fallos: si el servidor de un grupo se cae durante unos segundos mientras otro grupo sigue enviando, ¿cuántos mensajes se pierden o se duplican? La respuesta exige algo más que “guardar en una base de datos”: hace falta una cola persistente, un identificador estable, deduplicación, un reloj lógico y un mecanismo de recuperación.

1.2 Objetivos

  • Implementar el contrato mínimo de chat federado del curso.
  • Persistir usuarios, historial, reloj de Lamport y cola de salida.
  • Garantizar entrega al menos una vez y deduplicación por UUID.
  • Medir pérdidas, duplicados y tiempo de recuperación ante una caída controlada.
  • Documentar la arquitectura, las pruebas, la interoperabilidad y las limitaciones.

1.3 Alcance

El alcance es una sala global, #general, con usuarios locales y federación a través del central. No se implementan salas múltiples, mensajes directos, autenticación ni TLS. El centro de prueba del repositorio es para desarrollo; no reemplaza el central oficial del curso.

El profesor indicó que lo que debía entregar el script de conformidad se omite. Por eso este informe no anexa una salida oficial de conformidad. La evidencia local son las 53 pruebas, la corrida real del experimento y el ensayo local de interoperabilidad.

2. Marco conceptual

2.1 Arquitectura en estrella

En una arquitectura en estrella, un nodo central media todas las comunicaciones. Los servidores de grupo no necesitan conocer las direcciones de los demás: solo se registran en el central y reciben de él los mensajes. La ventaja es el desacoplamiento; la desventaja es que el central es un punto único de fallo. El proyecto lo mitiga con heartbeat, cola local y recuperación de historial, no con replicación del central.

2.2 Reloj de Lamport

Los relojes físicos de las máquinas no están sincronizados. Para ordenar eventos se usa un reloj lógico de Lamport. Las reglas implementadas son: 

Al emitir:  L = L + 1
Al recibir: L = max(L, L_recibido) + 1

El reloj se persiste en SQLite después de cada cambio. Si no se persistiera, al reiniciar podría retroceder y romper el orden. El historial se ordena por (lamport, origin, id): los dos primeros campos dan el orden lógico y el UUID desempata de forma determinista.

2.3 Entrega al menos una vez e idempotencia

El emisor no puede distinguir entre “la petición no llegó” y “la petición llegó, pero se perdió la respuesta”. Por eso reintenta. El receptor debe tolerar el mismo mensaje varias veces. La clave es el id: se genera una sola vez en el origen, viaja sin cambios en todos los reintentos y es clave primaria en SQLite. La inserción usa INSERT OR IGNORE; si el UUID ya existe, no se modifica el historial ni el reloj.

2.4 Outbox, backoff y heartbeat

  • Outbox: cola persistente de mensajes locales que aún no fueron aceptados por el central. Se elimina solo después de un 2xx.
  • Backoff exponencial con jitter: evita reintentos sincronizados y el efecto thundering herd.
  • Heartbeat: consulta periódica a GET /health del central. Tras varios fallos consecutivos se marca caído; al volver, se recupera el historial antes de seguir.
  • 4xx: se descarta y se registra DESCARTE_4XX; no se reintenta.
  • 5xx o error de red: se reintenta con el mismo UUID.

5.4 Formato del mensaje

{
  "id": "6f1c2a9e-4b7d-4f0e-9a51-2c8e7d3b1f44",
  "from": "ana@g3",
  "origin": "g3",
  "lamport": 42,
  "sent_at": "2026-11-10T14:03:22Z",
  "body": "¿Ya subieron el compose?"
}

id es un UUID generado en el origen y nunca cambia. from identifica al usuario con su grupo. origin es el servidor que originó el mensaje. lamport es la marca lógica. sent_at es solo informativo y no se usa para ordenar. Los campos desconocidos se ignoran.

5.6 Decisiones de diseño

  • Estrella: el enunciado prohíbe que los grupos se hablen directamente; el central define el orden global.
  • Deduplicación atómica: INSERT OR IGNORE sobre la clave primaria; si el UUID ya existe, no cambia nada.
  • Outbox persistente: el mensaje se elimina solo después de un 2xx; si el proceso muere, se reenvía con el mismo UUID.
  • Backoff con jitter: min(cap, base · 2^(n-1) · U(0.5, 1.5)); el segundo min mantiene el tope real.
  • Lamport persistente: el reloj no retrocede al reiniciar; el historial se ordena por (lamport, origin, id).
  • 4xx no se reintenta: se descarta y se registra DESCARTE_4XX; un 5xx o error de red sí se reintenta.

6.2 Reintentos: 5xx, 4xx y mismo UUID

Se verificó el siguiente comportamiento con un servidor de prueba:

  • Dos respuestas 500 y luego 200.
  • Tres intentos con el mismo UUID y esperas de 1.047 s y 2.566 s.
  • Al final, pending_messages = 0.
  • Un 400 se descarta con DESCARTE_4XX, sin reintento.

Esto confirma que el backoff se aplica y que el UUID no cambia entre intentos. La evidencia está en docs/PRUEBA_REINTENTOS.md.

6.3 Heartbeat y recuperación

El heartbeat consulta el central cada 5 s. Tras tres fallos consecutivos se marca caído; al volver, el grupo recupera el historial antes de continuar. En la prueba de caída controlada, el sistema volvió a en_linea = true sin intervención manual.

6.4 Persistencia

Tras docker compose restart, los usuarios, el historial, el reloj de Lamport y la cola de salida siguen en el volumen chat_data. El reloj no vuelve a cero: el siguiente mensaje continúa desde la última marca.

7. Experimento de caída y recuperación

7.1 Pregunta e hipótesis

Pregunta: ¿cuántos mensajes se pierden o se duplican cuando el servidor de un grupo se cae durante unos segundos mientras otro grupo sigue enviando?

Hipótesis: con una outbox persistente, UUID estables, deduplicación y recuperación por historial, no deberían aparecer duplicados y las pérdidas deberían ser nulas o mínimas. El resultado observado se reporta abajo: la hipótesis se cumple parcialmente.

7.2 Método

  • Emisor: g3b en http://localhost:8002.
  • Receptor sometido a caída: g3 en http://localhost:8001.
  • Central: central de prueba del docker-compose.yml.
  • Carga: 40 mensajes por repetición a 2 mensajes por segundo.
  • Caída: 5 s configurados, iniciada a los 5 s.
  • Repeticiones: 3.
  • Modo: docker compose stop / docker compose start; skip_docker: false.

El script registra los UUID enviados y los compara con el historial de g3. Calcula enviados, mensajes durante la caída, perdidos, duplicados y tiempo de recuperación. La caída efectiva se mide entre stop y start.

7.4 Análisis de las 7 pérdidas de la repetición 1

En la repetición 1 se enviaron 40 mensajes; 13 ocurrieron durante la caída. El historial final de g3 no contenía 7 de los UUID enviados y el script marcó recovered: false. La caída efectiva fue de 6.547 s, superior a los 5 s configurados. No hubo errores de envío (send_errors: 0) ni duplicados (duplicates: 0).

Explicación compatible con la evidencia: la recuperación de la ventana de caída fue incompleta. El receptor volvió y el emisor drenó su cola, pero la verificación final no encontró esos 7 mensajes en g3. El JSON no conserva la marca last_history_lamport ni las trazas de los reintentos de /history, así que no es posible aislar una causa única con los datos guardados. No se debe afirmar una causa que la evidencia no permite sostener.

La pérdida es de 7/120 = 5.8 %. Las repeticiones 2 y 3 no perdieron mensajes y las tres tuvieron 0 duplicados. Por eso el resultado global no puede presentarse como “cero pérdidas”; la lectura correcta es que la deduplicación funcionó y que la brecha está en la recuperación de la ventana de caída.

Dato que no debe usarse: la corrida experiment_20261115T033152Z se ejecutó con --skip-docker, envió solo 2 mensajes por repetición y no provocó caída. Sirve para validar el script, no como evidencia de resiliencia.

8.3 Qué funcionó

  • Registro y renovación del registro de ambos servidores.
  • Envío de g3b al central y reenvío del central a g3.
  • Cola outbox persistente: g3b no perdió mensajes mientras g3 estaba caído.
  • Recuperación por historial: g3 incorporó los mensajes posteriores a su reaparición.
  • Deduplicación por UUID: el historial no mostró mensajes repetidos.
  • Orden lógico por (lamport, origin, id).
  • Heartbeat y reintento: el sistema volvió a en_linea sin intervención manual.

9. Discusión de resultados

La hipótesis se cumple parcialmente. La deduplicación fue efectiva en las tres repeticiones: no hubo un solo duplicado. Dos de las tres repeticiones recuperaron todos los mensajes. La primera perdió 7, por lo que el resultado global no es “cero pérdidas”.

El patrón observado es compatible con una brecha en la recuperación de la ventana de caída, no con un fallo de idempotencia ni con un problema de ordenamiento. El emisor drenó su cola y el receptor volvió, pero la verificación final no encontró esos 7 UUID. Para explicar la causa raíz haría falta instrumentar la marca de historial, la ventana de recuperación y los reintentos de /history.

La recuperación media fue de 1.808 s. La caída efectiva superó los 5 s configurados en las tres repeticiones (6.547 s, 6.578 s y 6.547 s), lo que muestra que el tiempo real de docker compose stop/start no coincide exactamente con el valor nominal. Esa diferencia debe considerarse al interpretar el tiempo de recuperación.

10. Limitaciones

  1. SQLite y un solo proceso por servidor. No soporta varios workers; para producción haría falta PostgreSQL o Redis con restricción única y transacción para el reloj.
  2. Sin autenticación. Cualquiera que alcance el puerto puede crear usuarios o inyectar mensajes federados. En el aula se confía en la red; para producción haría falta API key o mTLS.
  3. HTTP sin TLS. El central del curso puede usar HTTPS; el servidor local no lo configura.
  4. Central único. Es un punto único de fallo. El proyecto tolera su caída temporal con cola y heartbeat, pero no su pérdida definitiva.
  5. Historial completo al arrancar. Es correcto y simple, pero costoso si el historial crece mucho. Se podría paginar o usar marcas por origen.
  6. Marca incremental de historial. Puede dejar huecos si llega un mensaje con Lamport muy alto antes que otros más bajos y el proceso no se reinicia; al reiniciar se hace sincronización completa.
  7. Central de prueba en memoria. No sirve para una sesión oficial; solo para desarrollo.
  8. Brecha de recuperación observada. La primera repetición perdió 7 de 40 mensajes y terminó con recovered=false. La evidencia no conserva la marca de historial ni las trazas de /history, así que no se pudo aislar la causa exacta.
  9. Sin salas ni mensajes directos. El enunciado pide una sola sala, #general; se mantuvo así a propósito.

11. Conclusiones y trabajo futuro

11.1 Conclusiones

  1. Arquitectura y protocolo: la estrella con HTTP/JSON, UUID, outbox e historial es una base coherente y desacoplada.
  2. Hipótesis parcial: se confirma la ausencia de duplicados, pero no la ausencia total de pérdidas; la primera repetición perdió 7 mensajes.
  3. Tolerancia y orden: Lamport persistente, orden (lamport, origin, id) y deduplicación evitaron duplicados; la brecha está en la recuperación de la ventana de caída.
  4. Reproducibilidad: Docker Compose, el script, JSON/CSV y 53 pruebas permiten repetir y auditar; falta instrumentar mejor la marca de historial y la ventana de recuperación.

11.2 Trabajo futuro

  1. Instrumentar last_history_lamport, /history y la ventana de recuperación para explicar las pérdidas tempranas.
  2. Integrar y validar con el central del curso y varios grupos, si el curso retoma la sesión oficial.
  3. Marcar los mensajes descartados por 4xx, añadir TLS/autenticación y probar en varios equipos.
  4. Evaluar PostgreSQL/Redis para varios workers y paginación del historial.
  5. Medir con más repeticiones y distintas duraciones de caída (2, 5, 10 s) para determinar si la pérdida es esporádica o sistemática.
